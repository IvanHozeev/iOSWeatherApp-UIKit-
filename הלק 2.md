# iOS Developer Mid Level Test - External Public API Access - Answers

## 1. Networking (רשת)

## שאלה: מה ההבדל בין URLSession ל-Alamofire? מתי תשתמש בכל אחד מהם?

## Answer:

URLSession is Apple's native and built-in API for networking. It provides robust, foundational functionality for making HTTP requests, uploads, and downloads, and it integrates well with Swift Concurrency (async/await).

Alamofire is a popular open-source third-party library that provides convenient wrappers (Syntactic Sugar) over URLSession. It simplifies many common networking tasks like building requests, handling responses, authentication, and file uploads.

When I would use them:

URLSession: In most cases and for new projects, especially with Swift Concurrency. It offers full control, reduces dependency on third-party libraries, and allows for clean and efficient code.

Alamofire: Only if it's already in use in an existing project, or for very complex projects with extensive needs for Alamofire's advanced features (like custom Interceptors or built-in error handling logic).

## שאלה: איך היית מטפל בשגיאות רשת במקרים של חיבור אינטרנט לא יציב?

## Answer:

When dealing with unstable internet connections (as in the example weather app), I would handle network errors by:

Offline Mode: Implementing the ability for the application to operate in an offline state. This means:

Caching Data: Storing the last successfully downloaded data using a local persistence layer (e.g., CoreData or SwiftData).

Displaying Cached Data: When there's no connection, the app will display the data stored on the device.

Network Monitoring: Using NWPathMonitor (from Network.framework) to continuously detect changes in the connection status.

User Notification: When the connection is lost, I can display a clear message to the user that the app is operating offline and that the displayed data might not be up-to-date.

Automatic Refresh: When the connection is restored, the app will attempt to refresh the data automatically from the API.

Specific Error Handling: Using a custom enum for network errors (e.g., NetworkError with cases like noInternetConnection, invalidResponse) to handle different failure states differentially.

## 2. Handling Data (טיפול בנתונים)

##  שאלה: מדוע כדאי להשתמש ב-CoreData לאחסון נתונים במקום UserDefaults?

## Answer:

The choice between CoreData and UserDefaults depends on the type and quantity of data we are storing, the complexity of relationships between them, and future implementation needs.

UserDefaults: Suitable for storing small and simple quantities of data, primarily user preferences (e.g., app settings, dark/light mode). It's an easy and quick solution for data that doesn't require a complex structure.

CoreData: Designed for storing large and complex quantities of data, including custom objects and their relationships (one-to-many, many-to-many). It provides powerful capabilities for efficient queries, filtering, sorting, and updating data. In these cases, using UserDefaults would be overkill and lead to performance issues and data management complexity.

In summary, for custom objects or any structured data with the potential for growth or relationships, it is recommended to choose CoreData (or the more modern SwiftData).

## שאלה: כיצד תנהל נתונים שהגיעו מה-API כדי לשמור על ביצועים גבוהים?

## Answer:

To maintain high performance when managing data received from an API, I would focus on three key principles:

Caching Data: Data received from the API would be immediately stored locally (in CoreData/SwiftData or an image cache). This would allow for quick loading of data on subsequent accesses, even offline, and prevent unnecessary network requests.

UI-specific Models: After receiving data from the API (and the dedicated Codable models for the API response), I would convert it into lighter, internal models (e.g., CityWeather instead of OpenWeatherResponse). These models would be specifically tailored for display and local persistence needs, reducing overhead and improving performance.

Correct Asynchronous Operation:

async/await / GCD: All network operations, heavy data parsing, and I/O operations with the local database would be performed asynchronously on separate threads (Background Threads) using async/await or DispatchQueue.global().async.

MainActor: User interface updates would always be performed on the Main Thread (using @MainActor or DispatchQueue.main.async) to prevent UI blocking and errors.

TaskGroup: For executing multiple API requests concurrently, I would use TaskGroup to leverage parallelism and improve overall loading time.

## 3. Architectural Patterns (דפוסי ארכיטקטורה)

## שאלה: מדוע כדאי להשתמש ב-MVVM בפרויקטים מורכבים?

## Answer:

I think this is a trick question, similar to the one about CoreData vs. UserDefaults. There's no absolute rule that MVVM must be used in complex projects. It simply depends on the project's complexity; we need different levels of application layering. MVVM is not the highest level of complexity, and I wouldn't say it's entirely optimal on its own. I use MVVM+C, and I find that to be a good approach in itself.

## 4. Offline Mode (מצב לא מקוון)

## שאלה: איך היית מוודא שהאפליקציה פועלת במצב לא מקוון בצורה מיטבית?

## Answer:

I would test it without an internet connection. This involves:

Physical Disconnection: Activating Airplane Mode on the device/simulator.

Scenario Testing: Ensuring all relevant screens display cached data.

Interaction Handling: Verifying that network-dependent actions are disabled or show an appropriate error message to the user.

Automatic Refresh: Checking that the app automatically refreshes once the connection is restored.

Unit/Integration Tests: Writing unit and integration tests that simulate various network conditions (including no connection) to verify the app's behavior.

## Answer:

Exactly as I do in the WeatherApp. There is a Network Check. If there is a network connection, I send a request to the API, receive data, and update the cache with it.
